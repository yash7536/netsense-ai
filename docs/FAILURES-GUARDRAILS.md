# NetSense AI — Failure Modes & Guardrails

This document answers two questions an AI product manager has to answer honestly, not just an engineer:

> Where can this product give an operator an incorrect, incomplete, stale, or misleading understanding of network health — and what should the product do about it so the operator isn't misled or the system doesn't act unsafely?

It builds directly on [EVALUATION.md](EVALUATION.md) (which found a real failure, not a hypothetical one) and [PROBLEM.md](PROBLEM.md) (which defines the workflow this failure sits inside). No application code changes as a result of this document — every failure mode below is either already evidenced by the evaluation or is a structural property of the architecture as it exists today, verified by reading the actual source, not assumed.

## Part 1 — Failure Mode Inventory

### Failure Mode A — Temporal instability (point-in-time scoring misses oscillation)

**What fails:** the anomaly detector can read a corridor as healthy while that corridor is, by its own incident record, actively unstable.

**Why it fails:** `computeVitals()` scores exactly one telemetry instant — "now" (`t = 0`). It has no concept of variance, oscillation, or rate-of-change across recent samples. A corridor whose instability is periodic (a flapping BGP peer, an intermittently-degrading amplifier) can have its "now" sample land on a quiet point in the cycle, and the detector has no way to know it just did.

**What the operator experiences:** they open Overview or Network Links and see the corridor reading healthy. If they already know about the open incident on that corridor, the product just told them something that contradicts what they know. If they don't know about the incident yet, they have no reason to look for it — the one screen that's supposed to tell them "this needs attention" didn't.

**Severity of user impact:** High. This isn't a subtle statistical edge case — it happens on the product's two most-trafficked screens, and it's a false negative on exactly the failure type (intermittent instability) that matters most to catch early.

**Evidence:** [EVALUATION.md](EVALUATION.md) Part 1 (Bengaluru–Hyderabad Core's `oscillation` profile scored 0.16, below the 0.22 threshold) and Part 2 (that same corridor has an open, high-severity incident, INC-395, with no live corroborating signal).

**Current, future, or hypothetical:** **Current.** This is not a hypothetical edge case — it happens deterministically, every time, for this corridor's telemetry as it exists in the dataset right now.

### Failure Mode B — Authored-vs-computed inconsistency

**The architectural seam:** anomaly score, health score, and healthy/attention state are computed live from generated telemetry. Prediction severity, prediction confidence, fault labels, incident severity, and engineer assignment are fixed, authored demonstration content — not generated by the detector, not kept in sync with it by any code path. Nothing enforces agreement between the two layers; nothing here is a machine-learning model producing an incorrect output, so this should not be described as a hallucination — it's a **product consistency risk created by having two layers that look unified but are wired independently.**

**Potential failure:** the authored layer can say something the live layer doesn't support.

- **Minor — PRD-102:** authored severity "medium," but the linked corridor's live anomaly score is 0.44 ("strong" by the evaluation's own heuristic). Understates urgency; doesn't contradict it.
- **Major — INC-395:** authored severity "high," status "investigating" (open), but the linked corridor's live state is healthy (score 0.16). This is a direct contradiction, not an understatement.

**Current, future, or hypothetical:** **Current and structural.** It isn't a one-off data-entry mistake — it's an inherent property of an architecture where one layer is computed and the other is authored, and it will recur for any future authored record added without a live check. The consistency-audit script (`app/scripts/eval-consistency-audit.ts`) exists specifically because this class of drift isn't self-evident by reading the dataset — it has to be checked.

### Failure Mode C — Limited signal coverage

**What this means:** the anomaly score is a weighted function of exactly four metrics — latency (40%), packet loss (30%), jitter (15%), bandwidth utilisation (15%). That's the entire input space. A fault that doesn't materially move one of those four numbers is invisible to `computeVitals()` by construction, no matter how real or severe it is. (The product does display richer physical-layer narrative — route topology, optical amplifier notes — but none of that feeds the scoring function; it's presentation content, not detector input.)

**Framing:** this is a **coverage limitation**, not a bug — a four-metric scoring model is a reasonable, legible v1 scope choice. The risk is purely one of disclosure: if it's not stated plainly, someone could reasonably assume the detector "sees everything," and it doesn't.

**Evidence:** the formula itself (`engine/netsense/scoring.py`, mirrored by `src/lib/derive.ts`) — no other metric exists anywhere in the telemetry data model (`TelemetryPoint` has exactly these four fields).

**Current, future, or hypothetical:** **Current and structural**, and currently dormant — all six designed drift profiles in the dataset happen to express themselves through these four metrics, so this gap hasn't produced a visible miss yet. It would the moment a fault type outside this input space was modeled.

### Failure Mode D — Missing or incomplete telemetry

**Checked directly against the code:** the Python generator (`engine/netsense/telemetry.py`) always emits a complete, deterministic series of 121 samples per link — every field clamped to a valid range, no nulls, no gaps, no malformed values — and the app reads that committed JSON. Neither the generator nor the scorer has a missing-data path: `getTelemetry()` in the app throws if a link has no generated telemetry (a build-time failure, not a graceful on-screen state), and there is no null/undefined handling for an incomplete "now" sample — not because the failure was handled and hidden, but because the generator was never built to produce it.

**Current demonstrated behavior:** telemetry is always complete in this prototype. The "missing or malformed data" scenario has never occurred, been tested, or been handled — not even defensively.

**Production-relevant future failure mode, clearly distinguished from the above:** a real telemetry pipeline — real collectors, real agents, a real network path to the monitoring system itself — routinely produces partial outages, agent downtime, and malformed samples. If `computeVitals()` were ever handed an incomplete "now" reading today, the likely outcome is silent `NaN` propagation into the anomaly score, not a graceful message — because no code path currently checks for that condition. **This is not something the current system handles; it's something a real deployment would need to handle before it could be trusted.**

### Failure Mode E — Confidence ambiguity

**How confidence is actually used today, checked against every reference to `confidencePct` in the codebase:**
- Displayed as a raw percentage on every prediction card and detail view.
- Used as a **secondary sort key** (Overview's top-signals ranking, and the Predictions table's confidence sort column).
- Shapes the geometry of one chart — `RiskHorizonMini`'s inflection point on Prediction Detail (a real, live computation from the actual `confidencePct` value, but purely visual).

**What it does not do:** gate whether a prediction is shown, change how prominently or urgently it's rendered relative to other predictions, or affect any downstream step in the workflow. **Confidence is displayed, sortable, and shapes one chart — but it is not currently used as a decision gate anywhere in the product.**

**Why this matters:** a 72%-confidence prediction (PRD-105) and a 91%-confidence prediction (PRD-104) get the same card treatment, the same visual weight, the same prominence — differing only in the printed number. An operator scanning quickly has no visual cue telling them to weigh the two differently; they'd have to read and mentally compare the percentages themselves every time.

## Part 3 — Guardrails

### Existing guardrails (verified against the actual implementation, not assumed)

- **Human review remains required everywhere.** No code path in `src/` or in the Python engine creates an incident, resolves an incident, reassigns an engineer, or triggers remediation automatically (a test fails if an engine function is named like an action). The incident page's operator-note box appends text to the displayed timeline only; it is local to the browser session and changes no record. This isn't a policy constraint layered on top of an autonomous system — the autonomous system doesn't exist.
- **No automatic incident creation from a prediction**, or vice versa — predictions and incidents are separate authored records connected only by a reference field (`relatedIncidentId` / `originatingPredictionId`).
- **No automatic incident resolution or severity change** based on live telemetry — `Incident.status` and `Incident.severity` are static authored fields; nothing recomputes them.
- **No automatic engineer assignment based on the anomaly score or anything else** — `assignedIncidentId` is a static field on each engineer record; no matching function exists anywhere in the codebase.
- **Deterministic scoring is fully inspectable** — `computeVitals()` is plain, readable arithmetic, not a black box; its Python reference implementation (`engine/netsense/scoring.py`) is exercised directly by the evaluation harness and held to the app's TypeScript scorer by exact-equality parity tests.
- **Evidence is visible to the operator**, not just a verdict — telemetry charts, evidence tiles, and incident timelines are real, navigable product surfaces, not summarized away.
- **The synthetic/demo nature of the data is disclosed** in `README.md` ("Product Truth," "Limitations / Disclosure").
- **Absence of data is shown honestly as absence**, not fabricated — `EmptySignal` on Link Detail explicitly states "No predictive signal has ever targeted this corridor" / "No incident has ever been logged on this corridor" when there's genuinely nothing there. (Note the boundary: this covers *zero records*, not *existing records that conflict with the live signal* — that gap is exactly Failure Mode B/INC-395, and nothing currently fills it.)
- **A standing, rerunnable consistency check now exists** (`python -m netsense evaluate`; `python -m netsense check` and the pytest suite fail if the committed results or generated app data drift) — a real, rerunnable mechanism for catching this exact class of failure before it's presented as settled fact. It detects; it does not prevent.

### Recommended future guardrails (not implemented — evaluated here, scoped as future work)

1. **Temporal evidence guardrail.** If the current snapshot and recent telemetry history disagree, surface that uncertainty rather than presenting the single snapshot as definitive. Directly justified by Failure Mode A / INC-395 — this is the detector-internal half of the fix.
2. **Confidence gating / visual de-emphasis.** A low-confidence prediction should not be presented with the same visual decisiveness as a high-confidence one. Directly justified by Failure Mode E.
3. **Insufficient-telemetry fallback.** If required telemetry is missing or malformed, show an explicit "insufficient evidence" state instead of computing and presenting a confident-looking score from partial input. Justified by Failure Mode D — precautionary, since the condition can't occur in the current demo, but necessary before any real telemetry source is connected.
4. **Signal/incident conflict surfacing.** If a corridor's live health state and an active incident's authored severity materially disagree, surface that conflict for human review rather than silently displaying both without comment. Directly justified by Failure Mode B / INC-395 — this is the product-layer half of the fix, related to guardrail #1 but operating across records rather than within one detector's internal history.

None of the four above are implemented. They are recommendations this evaluation justifies, not commitments made in this document.

## Part 4 — Fallback Behavior

The governing principle: **when evidence becomes unreliable, the product should reduce how decisively it presents a conclusion and increase transparency — never increase automation.** The fallback is never "the system decides anyway."

| Failure | Preferred Behavior | If Evidence Is Insufficient / Conflicting | Human Action |
|---|---|---|---|
| A — Temporal instability | Detector's live score reflects sustained state accurately | *(future)* Flag when the latest snapshot and recent history disagree, instead of only ever showing the latest instant | Operator still makes the call; the product's job is to stop hiding the disagreement, not to resolve it |
| B — Authored/computed conflict (INC-395-class) | Authored severity and live signal agree | *(future)* Show an explicit "live telemetry does not currently corroborate this incident" notice rather than presenting both silently | Operator decides whether to deprioritize, keep investigating, or treat as resolved — never auto-decided |
| C — Limited signal coverage | The 4 monitored metrics capture the fault | Currently silent if a fault falls outside those 4 metrics — no gap indicator exists | Operator's own domain knowledge and other tooling has to cover fault types outside this product's disclosed scope |
| D — Missing telemetry | Complete, valid telemetry (today's guaranteed reality) | *(future)* Show an explicit "insufficient telemetry" state rather than computing a score from partial/undefined input | Operator falls back to other tooling until telemetry resumes; the product should never present a confident score built on incomplete input |
| E — Confidence ambiguity | Confidence is high and evidence is strong | *(future)* De-emphasize low-confidence predictions visually rather than matching high-confidence presentation | Operator still decides how much to trust it; the product's job is to stop implying equal certainty across different confidence levels |

## Part 5 — Product Decisions

| Failure | Decision | Reasoning |
|---|---|---|
| A — Temporal instability (INC-395) | **Fix later** — prioritize temporal/rolling-window-aware anomaly scoring as a named roadmap item | Matches the decision already recorded in `EVALUATION.md`. Retuning the synthetic data to make this pass, or changing `computeVitals()` right now, would either hide the finding or make it impossible to tell whether the fix addresses the real root cause. Not done in this task. |
| B — Authored/computed inconsistency | **Document limitation** (PRD-102, general architecture) + **fix later** (the specific conflict-surfacing mechanism, item #4 above) | The authored/computed split is a deliberate, disclosed architecture choice — not itself a bug to remove. The *lack of a conflict-surfacing mechanism* is the gap worth fixing, later, as scoped work. |
| C — Limited signal coverage | **Document limitation** | A reasonable v1 scope boundary. Expanding signal coverage is a real future direction, not an urgent fix — nothing in the current dataset has exposed a live miss from it yet. |
| D — Missing/incomplete telemetry | **Document limitation now; treat as a prerequisite before any real-data integration** | Not reachable in the current demo, so not urgent today — but unlike the others, this one becomes a blocking requirement, not an optional improvement, the moment real telemetry is ever connected. |
| E — Confidence ambiguity | **Monitor / document** | Genuine but low-severity. A plausible small future refinement, explicitly not built now, since it wasn't identified as causing a concrete failure in the current evaluation the way A and B were. |

## Part 6 — Connecting This to the Evaluation

This document doesn't invent a theoretical failure list after the fact — Failure Mode A and the major half of Failure Mode B were **found by running the evaluation**, not reasoned about in the abstract:

```
Evaluation (EVALUATION.md, Part 1: drift-profile classification)
  → oscillation profile resolves as "healthy" at t=0 (score 0.16, below the 0.22 threshold)
    → Evaluation (EVALUATION.md, Part 2: authored-vs-computed audit)
      → same corridor's INC-395 is an open, high-severity, still-investigating incident
        → named as a temporal blind spot: a healthy score (~0.16) beside an active high-severity incident
          → user impact: an operator sees a direct, visible contradiction between the corridor's
            live status and its own incident record — on the two screens most likely to be checked
            together
              → guardrail implication: the product correctly takes no automatic action on this
                conflict today (no auto-resolve, no auto-suppress) — the gap is that it also
                doesn't currently *say* the conflict exists
                  → future product decision: scope temporal/rolling-window scoring (fixes the
                    detector) and conflict-surfacing (fixes how the product communicates when the
                    detector and the record set disagree) as two related, named roadmap items —
                    not implemented now
```

Failure Modes C, D, and E were identified by reading the architecture directly (not evaluation output), but are held to the same standard: each is verified against actual code, none are hypothetical dressed up as findings, and none are fixed here.

## Part 7 — Portfolio Version

For inclusion in the eventual case study, in short form:

> I didn't assume NetSense's detection layer was correct just because the demo looked right. I evaluated it against telemetry scenarios I designed the expectations for in advance, and it found a real failure: an oscillating corridor that the detector reads as healthy while its own incident record says otherwise. I named it a temporal blind spot — the scorer reads one instant — and considered the fix, and rejected the two easy paths (retuning the demo data, or patching the detector immediately) because either would have hidden what the evaluation was actually for. Instead I documented the failure, worked out what the product should and shouldn't do when its own layers disagree, and turned the finding into two specific, evidence-backed items for the roadmap. The product still tells the truth about what it doesn't know how to do yet — that's the part I think matters most here.
