# NetSense AI — AI / Automation Workflow

This document answers the third of the seven AI PM requirements: where does automation actually sit in this product, what does it do at each stage, and where does a human take over. It consolidates content that previously lived split across `README.md`'s "Product Workflow" and "Detection Approach" sections into one place, so the workflow, the deterministic/authored boundary, and the human control point can be evaluated together — see [EVALUATION.md](EVALUATION.md) for whether it works and [FAILURES-GUARDRAILS.md](FAILURES-GUARDRAILS.md) for where it doesn't.

## The Pipeline

```
Input                Seeded synthetic telemetry per link, generated by the Python engine (48h trailing + 12h synthetic continuation, 30-minute samples)
  → Processing        Baseline-deviation scoring: latency/loss/jitter/bandwidth → composite anomaly score
    → Detection       Threshold check (0.22) → healthy / attention state
      → Evidence      Telemetry charts, evidence tiles, per-metric emphasis — the numbers behind the verdict
        → Context     Prediction (severity, confidence, narrative) and Incident (status, timeline, owner),
                       cross-referenced to the link and to each other
          → Human Review    Operator reads the signal, the evidence, and the context together
            → Decision      Operator decides what happens next — the product stops here
```

Every arrow above is a real, traversable relationship in the product (a prediction always links back to its link and forward to its incident; an incident always links to its originating prediction and its assigned engineer) — not a conceptual diagram describing something the UI doesn't actually do.

## What's Computed, What's Authored, What's Human, What's Future

This is the single most important table in this document, because collapsing these four categories into one ("the AI") is exactly what would misrepresent the product.

| Stage | What Happens | Category |
|---|---|---|
| Telemetry generation | A seeded, deterministic generator produces 48h+12h synthetic telemetry per link (the +12h samples are a synthetic continuation, not a forecast model) | **Computed** (deterministic, not ML) — Python: `engine/netsense/telemetry.py`; committed as JSON the app imports |
| Anomaly score / health score / healthy-vs-attention state | Weighted deviation from baseline (latency 40%, loss 30%, jitter 15%, bandwidth 15%), thresholded at 0.22 | **Computed** from the generated telemetry — Python reference (`engine/netsense/scoring.py`); the app's TypeScript scorer is held to it by exact-equality parity tests |
| Prediction severity, confidence %, fault label, narrative | e.g. "high severity, 91% confidence, Latency Instability" | **Authored** demonstration content — fixed values, not detector output |
| Risk-horizon curve shape (Prediction Detail) | Inflection point derived from that prediction's actual `horizonHours` and `confidencePct` | **Computed live**, from authored fields — a real calculation, but feeding on authored inputs |
| Incident severity, status, fault label, timeline | e.g. "high severity, investigating, BGP Peer Dampening" | **Authored** demonstration content |
| Link ↔ prediction ↔ incident ↔ engineer cross-references | Resolved from the shared dataset at render time so every screen agrees | **Computed** (lookup/consistency logic, not detection) |
| Display status and consistency flags | The worse of live state and any authored high/critical record on the corridor; flags such as `authored_severity_without_live_signal` | **Computed** (`engine/netsense/workflow.py`; the app's `aggregate.ts`) |
| Engineer assignment | Which engineer is linked to which incident | **Authored** — a static field, not the output of a matching algorithm |
| Evidence display (charts, tiles, timeline-to-chart linking) | Rendering the real telemetry and record data behind a claim | **Computed/rendered**, not authored narrative |
| What happens next | Opening, escalating, resolving, or dismissing anything | **Human**, always — no code path in the product does any of this automatically |
| Temporal/rolling-window-aware scoring | Evaluating variance or rate-of-change across a recent window, not just the latest sample | **Future** — documented as the next step; not built. Still deterministic logic if built, not ML. |
| A trained anomaly-detection model | Learning fault patterns from historical, labeled data | **Future, and further out** — see "Why Deterministic, Not ML" below for why this isn't the next step |

Nowhere in the current product does an authored field get described as model output, and nowhere does a computed field get treated as more authoritative than the evaluation shows it actually is.

## Why Deterministic Logic, Not Machine Learning

This is a product decision, not a limitation to apologize for.

A trained model needs three things this project deliberately doesn't have and won't fabricate: labeled historical outage data, a way to validate predictions against ground truth, and a real cost tradeoff between false positives and false negatives to tune against. None of that exists for a synthetic prototype, and inventing it (a fake training set, a fake accuracy number) would be worse than not having it — it would replace an honest, auditable rule with a dishonest, unauditable one.

A hand-written, weighted deviation rule, by contrast, is something this project can actually stand behind: every term is readable in about thirty seconds (`engine/netsense/scoring.py`, mirrored in `src/lib/derive.ts`), every output was checked against designed test scenarios (`EVALUATION.md`), and every failure the rule has could be explained by pointing at the exact line responsible (`FAILURES-GUARDRAILS.md`, Failure Mode A). That combination — inspectable, testable, explainable — is worth more at this stage than the appearance of a more sophisticated system that couldn't be evaluated with the same honesty.

This follows directly from the same principle that governs the rest of the product: **if a simple deterministic rule solves the problem better than an LLM or ML model, prefer the simpler approach.** Nothing about this problem, at this dataset's scale, currently justifies the added complexity, reduced explainability, and unvalidatable confidence that a trained model would introduce.

## Future AI Opportunities (Not Built)

Labeled explicitly as future direction, not current capability:

- **Temporal/rolling-window-aware scoring** — the evidence-backed next step from `EVALUATION.md`. Still a deterministic rule (evaluating variance/rate-of-change over recent samples instead of one instant), not a move to machine learning.
- **A trained anomaly-detection model** — a real future option, but a much bigger step, and one that would need: genuine historical, labeled fault data (not synthetic); a defined precision/recall tradeoff appropriate to an operations context; and a retraining/drift-monitoring plan so the model's own confidence stays trustworthy over time. None of these prerequisites exist yet, which is exactly why this stays a "future direction" and not a near-term plan.

## Human Review, Concretely

At no point in this pipeline does the product take an action — only present information. Verified directly against the code, not asserted: no function anywhere in `src/` or the Python engine (a test enforces this) creates an incident, changes an incident's status, reassigns an engineer, or triggers remediation. The `remediationMode` field shown on every prediction ("Advisory Only (Manual Gate)") and the explicit copy on Prediction Detail ("Automated changes are disabled... operator confirmation required") describe a real architectural property, not a policy layered on top of a system that could otherwise act on its own.
